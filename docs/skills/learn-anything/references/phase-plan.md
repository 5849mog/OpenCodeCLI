# 阶段一点五 + 阶段二 · 砍知识树、内部施工图与开场说明

> **何时读**：诊断题答完、准备规划路径前必读本文件。施工图填写示例直接附在本文件末尾。
> 这一步产出两样东西：内部施工图（速览/单元写在思考里不发不落；**长程写进状态文件**）+ 开场说明（发出去，等点选确认）。

## 阶段一点五 · 先砍知识树，再排路径

**学不完是常态，砍不动才是失败。** 一个领域的知识量总是大于用户的时间预算，所以第一步动作不是「列出该学什么」，而是「决定不学什么」。全都讲一点的结果是全都不会。

开讲前先定三样，写进施工图：

1. **一句能力目标** —— 必须是可验收的动作。「了解 Transformer」是主题不是目标；「能看懂一段 attention 代码在算什么」才是目标。判据很简单：目标句里得有一个能当场检验的动词。
2. **最小知识树** —— 20% 核心，外加**明确写出砍掉的 80%**。砍掉的要写出来给用户看，一是让他有机会喊回来（「这个我恰好需要」），二是防止你自己偷偷把它们塞回讲解里。
3. **掌握层级** —— 这次到哪一级（级别的定义与判定细则见核心文件「共享判据一 · L1–L6 判定细则」）。

层级不是越高越好，是要对上用途：应付选择题考试到 L3 够用，上手做事至少 L4，**而只要这个操作会影响到别人或线上环境（共享分支、生产数据库、真金白银），就必须到 L5**——这类知识里「知道什么时候不该做」比「会做」值钱得多，不划界等于给他一把没保险的枪。教别人或做技术决策要 L5–L6。**在内部施工图里写明这次到哪级，因为它直接决定每段的产出任务长什么样。**

第二条硬规则：

> 一个知识点说不出「不学它会卡在哪」，就该砍掉或降级成附注。

这条能拦住「顺便也讲讲历史背景 / 顺便提一下另外三种变体」——那些不是知识树，是你的联想。

## 阶段二 · A 内部施工图

**长程先建档**：预判为长程、回合 1 点选确认后，施工图不写在思考里，直接写进状态文件 `~/.learn-anything/sessions/<主题slug>.md`（目录不存在就建；更新与续学协议见 `phase-close.md`）。文件存在、字段齐全，施工图才算写过——这是长程的执行核查。速览和单元不落盘，施工图写在自己的思考里。

字段七个，一个都不能少，它是你后面每一段的施工依据和自检清单：

1. **目标行** —— 能力目标（一句可验收的话，带一个能当场检验的动词）+ 掌握层级（L1–L6）+ 为什么定这一级
2. **模式行** —— 知识类型 → 走哪一套（`methods/route.md`）+ 教学法来源（无可指认来源不许写）
3. **主线心智模型** —— 一个类比，全程只用它
4. **摸底结果与误解埋点** —— 他会什么、诊断题哪几题答错；埋点至少一条必须来自他本人的错误
5. **知识树** —— 最小知识树（学这些）+ 明确砍掉（这次不学）
6. **分段路径表** —— 每段：解决什么卡点 / 教学动作 / 要他产出什么 / 验收判据 / 时长
7. **复习与取舍** —— 哪段开讲前抽上一段哪题；因时间预算或环境限制砍了什么

每项都必须**具体到可执行**，不能写「打好基础」「深入理解原理」这种无法落地的词。具体性判据：**把某一段的「要他产出什么」单独抽出来，交给一个完全没听过讲解的人，他能明白要交什么，而你能明确说出交上来的对不对。** 写不出这种任务的段落，说明你自己也没想清这段要教什么——回去重切。

**施工图与开场说明是耦合的，这是执行核查**：开场说明的四要素（目标 / 几段 / 每段做什么 / 不学什么）就是字段 1、5、6 的机械投影。**写不出开场说明 = 没写施工图。** 发现自己在没有施工图的情况下动笔写开场说明，停下来，先补施工图。

**施工图不发给用户**，这个安排是刻意的：详细的路径规划是**你的施工依据**，跟编程前写的 plan 一样，是给执行者看的。用户不会逐项核对一张分段表，他习惯的是有人跟他说话。把施工图贴给他，他既看不懂那些内部刻度，也不会真的读——**你以为拿到了确认，其实只拿到了一句「嗯，可以」**。

## 阶段二 · B 开场说明（这才是发出去的）

3–5 句人话，说清四件事：**要达到什么**（用动作说，不用层级）、**大概分几段多久**、**每段完了要他做什么**、**这次不学什么**。

照着施工图，发出去的应该是这样：

> 我们这么走：先弄明白 rebase 到底动了什么，这块是后面所有操作的地基；然后你自己动手把三个提交压成一个；再制造一次冲突让你亲手解一遍；最后我会重点讲什么时候绝对不能用它——你说要用在真项目上，这条不讲清会伤到同事。
>
> 大概四段，一个多小时。每段完了我会让你做一遍或讲一遍，光听不算过。这次不碰 cherry-pick 和 reflog 救援，用得上再补。

**判据：把这段话给一个完全不懂教学法的人看，他能明白接下来会发生什么、以及你要他干什么。** 里面出现任何框架术语（阶段、层级、闸门、规格书、教学模式）就是没写对。

注意这段话里其实塞满了施工图的信息——目标、四段路径、每段的验收方式、砍掉项、以及为什么第 4 段重要——但一个内部术语都没有。**信息量不用减，只是换成他的语言。**

**发完用 `AskUserQuestion` 收确认**（行 / 想改一下 / 你定就行），然后这一回合结束。用点选而不是让他打字，是因为此时他对这个领域还没有判断力，面对一段规划让他「提意见」是在为难他；点选让他至少能表态。真要改的人走「其他」照样能写清改哪儿。

## 施工图填写示例（git rebase，技能操作类）

动笔前先照这份的密度和格式校准——别写「打好基础」「深入理解原理」这类无法落地的词。

```
目标行：能把一条乱掉的本地提交历史整理成干净的三个提交，并说清什么时候绝对不能这么做
        （L5 能划界——他说要用在真项目上，会影响同事，必须包含「什么时候不该用」）
模式行：技能操作类 →「最小可用闭环 → 刻意练习 → 撤脚手架」（Ericsson + worked-example fading）
主线心智模型：rebase 不是「移动分支」，是把提交一个个摘下来、在新基底上重放一遍。全程只用这一个模型
摸底结果与误解埋点：会 commit / push / 简单 merge；不知道 rebase 和 merge 的区别；
  诊断题第 3 题（共享分支）答错——重点段
  埋点：「rebase 和 merge 二选一」（解决的不是同一个问题）／「rebase 会丢代码」（丢的是提交对象
  不是内容）／「本地能 rebase，共享分支也差不多」（第 4 段核心，他本人就错在这）
知识树：
  学这些——重放模型：为什么 commit 哈希会变；interactive rebase 三个动作 pick / squash / reword；
  冲突发生时你在哪、怎么继续；铁律：已推送到别人会拉的分支上不许 rebase
  明确砍掉——rebase --onto 的三参数形式；cherry-pick、reflog 救援、autosquash；
  merge 策略与 fast-forward 的细节
分段路径表

| 段 | 它解决什么卡点 | 教学动作 | 要他产出什么 | 验收判据 | 时长 |
|---|---|---|---|---|---|
| 1 | 不知道 rebase 到底动了什么 | 重放模型 + 哈希变化演示 | 讲一遍为什么哈希变了 | 讲出「重放 = 新提交」，没说成「改了原提交」 | 10 min |
| 2 | 不会实操 squash | 给练习仓库，跟做一遍 | 自己把 3 个提交压成 1 个 | 贴回的 git log 只剩 1 个提交且信息正确 | 15 min |
| 3 | 冲突时不知所措 | 制造一次冲突，讲清「你在重放的第几步」 | 独立解决一次冲突并 --continue | 走完全程没有 --abort | 15 min |
| 4 | 会在共享分支上翻车（诊断题错点） | 反例：同事视角看到什么 | 说出三个「绝对不该 rebase」的场景 | 三个都成立，且能说出后果 | 10 min |

复习与取舍：第 3 段开讲前抽第 1 段的重放模型；本次为单元，不落盘；不碰 --onto
```

## 最该校的判据

把某一段的「要他产出什么」单独抽出来，交给一个完全没听过讲解的人，他要能明白要交什么，而你能明确说出交上来的对不对。写不出这种任务的段落，说明你自己也没想清这段要教什么——回去重切。
