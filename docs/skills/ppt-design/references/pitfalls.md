# 静默翻车清单

这里每一条的共同特征是：**不报错、文件正常生成、甚至预览也不一定看得出，但成品已经坏了。**

标注 ⚠️ 的是实战中真撞上过的，不是理论风险。

---

## 1. ⚠️ 字体被静默替换

**症状**：在你机器上预览正常，发给别人打开就排版散了、文字溢出、换行位置全变。

**原因**：写进 pptx 的只是字体**名字**。目标机器没有这个字体时，PowerPoint 会静默替换成别的，替换字体的字宽不同，于是所有换行和对齐都变。**这个过程没有任何提示**，而且你自己机器上有那个字体，所以你永远看不到问题。

**做法**：

- 只写目标机器一定有的字体。Windows + Office 自带的安全选择：`微软雅黑`、`宋体`、`黑体`、`等线`、`Arial`、`Arial Black`、`Impact`、`Georgia`、`Times New Roman`、`Consolas`、`Calibri`、`Segoe UI`、`Verdana`、`Tahoma`。
- `Noto Sans SC`、`思源黑体`、`思源宋体`、`LXGW 文楷` 这类**不是系统自带**，只能当兜底，不能当唯一字体名。
- 在**每一个** run 上显式设置字体（pptxgenjs 的 `fontFace`），不要依赖主题继承的字体。
- 中文避免 Light / Thin 字重：中文笔画比拉丁多得多，细字重在投影上会糊成一团。正文用 Regular，标题用 Bold。

**怎么验证**：动手前先列本机字体，核对你要用的确实存在。

```bash
ls /c/Windows/Fonts/ | grep -iE "msyh|simsun|simhei|dengxian|ariblk|impact|georgia|consola"
```

## 2. ⚠️ pptxgenjs 把 `blur: 0` 吞掉，硬阴影变柔和阴影

**症状**：你写了零模糊的硬阴影，导出后阴影却是柔的。文件正常、渲染正常、缩略图上还看不太出来，但如果风格依赖硬阴影（新粗野主义、拟物卡片），整页气质已经废了。

**原因**：pptxgenjs 源码里写的是

```js
shadow.blur = valToPts(shadow.blur || 8)
```

JavaScript 里 `0` 是 falsy，所以「我要零模糊」被当成「我没填这个值」，直接套上默认的 8pt 模糊。

**做法**：传一个极小的**真值**代替 0。

```js
const hard = (color = "111111", offset = 7) => ({
  type: "outer", color, blur: 0.0001, offset, angle: 45, opacity: 1.0,
});
```

`0.0001pt` 约等于 1 EMU（1/914400 英寸），实测等效于零模糊。

**怎么验证**：读导出文件的 XML，确认 `blurRad` 是 1 而不是 101600。

```bash
python -c "
import zipfile,re
x=zipfile.ZipFile('deck.pptx').read('ppt/slides/slide1.xml').decode('utf8')
b={int(re.search(r'blurRad=\"(\d+)\"',t).group(1)) for t in re.findall(r'<a:outerShdw[^>]*>',x)}
print('模糊值集合(EMU):',b,'→ 全硬' if b=={1} else '→ 有柔和阴影，需修')
"
```

**推广**：任何库里凡是「0 是有意义的值」的参数（blur、offset、charSpacing、indent、rotate），都要警惕 falsy 判断。给了 0 却不生效时，先去读源码。

## 3. ⚠️ 中文断行劈开词组

**症状**：出现「数据看板的常见版 / 式。」这种把「版式」劈成两半的换行，或者「故意错 / 位」、「粗 / 糙」。还常伴随一个两三个字的孤零零尾行。

**原因**：中文没有空格可以断行，自动换行只会按宽度硬切，切到哪算哪。

**做法**：

1. **窄栏文字一律用显式换行**，自己指定断点，不要交给自动换行。
2. 但显式换行意味着断点全由你负责，所以：**断点只能落在标点之后**（、，。；：！？—— 」）等）。
3. 算清每行容量：`容量(字) = 框宽(英寸) × 72 ÷ 字号(pt)`。全宽中文字符正好占 1em，拉丁与数字约 0.52em。
4. **一行超出容量会被二次折行**，把你精心指定的断点搞乱，甚至正好劈开一个词。所以每行都要留 5% 以上余量。
5. 中文文本框比同内容的拉丁文本框宽出约 15%。
6. 不要留下只有两三个字的尾行。

**实战教训**：这条我撞了两次，两次都是**我自己数错字**，不是自动换行失手 —— 手写换行数组时按字数硬切却忘了看词边界，以及把 15 个字数成 14 个导致折出第四行撑破箱体。所以必须靠 `qa.py` 的断点检查兜住，不要相信自己数得对。

**怎么验证**：`scripts/qa.py` 会逐行报出宽度占用，并在换行落在非标点处时告警。

## 4. 富文本数组每一项都要 `breakLine`

**症状**：PowerPoint 打开时第一帧正常，随后这一段文字自己重排、错乱。LibreOffice 渲染却完全正常，所以**PDF 预览抓不到这个问题**。

**原因**：pptxgenjs 的富文本数组是**每个 run 输出一个 `<a:pPr>`**，不是每段一个。两个以上不带 `breakLine` 的项会落进同一个 `<a:p>`，各自带一份段落属性，违反 OOXML 的 `pPr? (r|br|fld)* endParaRPr?` 结构。只有 PowerPoint 会因此重排。

**做法**：多行文本的每一项都给 `breakLine: true`（最后一项可省）。用一个辅助函数一次性解决：

```js
const lines = (arr, opts) =>
  slide.addText(
    arr.map((t, i) => ({ text: t, options: i < arr.length - 1 ? { breakLine: true } : {} })),
    opts
  );
```

**不要**用「把 run 拆成多个段落」来修 —— 那会把你设计的一行内混排变成两行，改变版式。

## 5. ⚠️ `addShape` 是幻灯片的方法，不是 presentation 的

**症状**：`p.addShape is not a function`，或者更糟：写成 `p.addShape.call(slide, ...)` 之类的绕法，看起来跑通了但行为诡异。

**原因**：`addSlide()` 返回的幻灯片对象才有 `addShape` / `addText` / `addChart`。presentation 对象只有 `addSlide` / `writeFile` / `shapes` / `charts`。

**做法**：辅助函数里用幻灯片变量，不要用 presentation 变量。注意 `pres.shapes.RECTANGLE`（形状枚举）确实在 presentation 上，别混淆。

## 6. 选项对象不能跨调用复用

**症状**：第一个形状正常，第二个形状的阴影或描边错乱。

**原因**：pptxgenjs **就地修改**传入的选项对象（比如把 pt 换算成 EMU 写回去）。共享同一个对象，第二次调用拿到的就是已被改写的值。

**做法**：用工厂函数，每次返回新对象。

```js
const edge = () => ({ color: "111111", width: 3 });   // ✅ 每次新对象
const EDGE = { color: "111111", width: 3 };           // ❌ 复用会被改写
```

## 7. 颜色写法会让文件损坏

- **不能带 `#`**：`color: "FF0000"` ✅ / `color: "#FF0000"` ❌ 直接损坏文件
- **不能把透明度编进 8 位 hex**：`"00000020"` ❌ 损坏文件。透明度用独立的 `transparency` 或 `opacity` 属性。

## 8. `rectRadius` 只在 `ROUNDED_RECTANGLE` 上生效

**症状**：给 `RECTANGLE` 设了圆角却没反应；或者小尺寸格子上圆角显得比例失调。

**原因**：`rectRadius` 只对 `ROUNDED_RECTANGLE` 有效。而且它的换算是相对于形状**较短边**的，所以同一个 `rectRadius` 值在 0.3 英寸高和 1 英寸高的格子上，视觉圆角比例完全不同。

**做法**：一组尺寸差异大的格子，圆角值要按尺寸分档，或统一取小值（0.03–0.05）避免小格子被啃掉。

---

## 9. 必须显式设置 `LAYOUT_WIDE`

**症状**：所有字号都溢出，排版系统性挤爆。

**原因**：pptxgenjs 默认是 `LAYOUT_16x9`，而它只有 **10 × 5.625 英寸**。所有主流字号建议（44–72pt 标题、16pt 正文）都是按 13.33 × 7.5 调的，画布小了 25% 而字号没变，必然溢出。

**做法**：每份文件开头显式 `pres.layout = 'LAYOUT_WIDE'`。若刻意用 10 英寸宽画布，所有字号和页边距乘 0.75。

---

## 10. 阴影 offset 不能为负

**症状**：文件损坏或阴影方向不对。

**做法**：`offset` 必须非负。要让阴影朝上投，用 `angle: 270` 配正的 offset，不要用负 offset。角度是从三点钟方向顺时针算：45 = 右下，135 = 左下，270 = 正上。

## 11. 堆叠柱状图不能用 `outEnd` 数据标签

**症状**：PowerPoint 打开时提示「需要修复」，修复后图表消失。LibreOffice 渲染正常，所以 PDF 预览抓不到。

**原因**：OOXML 规定 `dLblPos` 受图表分组限制 —— stacked / percentStacked 只允许 `ctr` / `inBase` / `inEnd`，`outEnd` 只对 clustered 合法。pptxgenjs 不会阻止你写错。

**做法**：要突出某一根柱子，用 `varyColors: true` 加 `chartColors` 逐点着色，配 clustered 分组：

```js
slide.addChart(p.charts.BAR, data, {
  barGrouping: "clustered",            // stacked / percentStacked 只许 ctr/inBase/inEnd
  barDir: "col",
  varyColors: true,
  chartColors: ["1F3A5F", "1F3A5F", "9B2226"],  // 逐点着色，最后一根是要突出的
  showValue: true, dataLabelPosition: "outEnd", // clustered 下 outEnd 才合法
  dataLabelFontSize: 12, dataLabelFontFace: "微软雅黑",
});
```

## 12. 多个模块的右边缘要锁同一个常量

**症状**：几个模块的右边缘差 0.05 英寸，看着说不出哪里别扭，但整页就是不整齐。

**原因**：各模块的 x 和 w 分别硬编码，加起来自然不对齐。

**做法**：定义 `const RIGHT = W - M;`，需要右对齐的模块统一用 `x = RIGHT - w` 推算。任何风格都适用，**尤其是刻意「乱」的风格** —— 新粗野主义的乱必须建立在严格对齐上，真的随便摆出来是廉价感而不是风格感。

---

## 13. 阴影和描边会吃掉视觉缝隙

**症状**：代码里算的间距明明够，渲染出来两个模块却像是贴在一起。

**原因**：阴影向右下偏移会占掉右侧和下方的缝隙；描边是**以边线为中心**向外扩一半宽度。两者都会压缩肉眼看到的空白。

**做法**：算「可见缝隙」时减掉这两项。

```
可见缝隙 = 标称间距 − 阴影偏移 − 描边宽度的一半（两侧各算）
```

例：标称 0.30 英寸，阴影偏 7pt（0.097 英寸），描边 3pt（外扩 0.021 英寸），实际可见约 0.18 英寸。

**做法上的经验**：模块之间的缝隙应当**大于**同组元素之间的缝隙（模块级分隔 > 兄弟级分隔），这个层次对了页面节奏才对。

## 14. 文字绝不能直接压在满幅图片上

**症状**：文字在图片亮部完全读不出来。

**做法**：图片 → 60–80% 不透明度的暗色遮罩 → 文字，三层顺序不能省。或者更稳的办法：把图片放在有界区域（比如右半边），文字放在纯色的另一半。

图片比例不符时**裁切，不要拉伸**（用 `sizing: { type: 'cover' }`）。拉伸变形是封面页上最显眼的缺陷。

**自检**：想象这一页用灰度打印，每个字还读得出来吗？

## 15. 派 judge 时必须声明刻意违反的规则
**症状**：judge 把你精心做的风格特征当缺陷报回来 —— 粗黑描边、高饱和撞色、刻意旋转全被标成问题。

**原因**：judge 默认按通用设计规范判，而多数有个性的风格恰恰是**故意**违反通用规范的。

**做法**：prompt 里明确列出「以下是用户指定风格的定义性特征，不是缺陷」，并附上设计意图（配色角色、字体字号体系、结构安排）。同时说明什么才算这个风格的真正失败（例如新粗野主义里，柔和阴影才是失败）。这样 judge 判的是「执行到不到位」，而不是「我喜不喜欢」。**prompt 按 `references/judge-prompt.md` 填空，不要现场即兴**——漏掉刻意违例声明是 judge 误报的头号原因。

## 16. ⚠️ 旋转形状的实际扫过范围远大于它的标称框

**症状**：一条倾斜的色带/光带，代码里明明放在两块文字之间的净空区，渲染出来却切穿了上方或下方的文字。qa.py 也查不出来——因为形状的**未旋转包围框**确实在画布内、也确实不与文本框重叠。

**原因**：`rotate` 绕形状中心旋转，一条又宽又扁的带子旋转后两端会在垂直方向甩出很远。python-pptx 与 qa.py 读到的是未旋转的 `left/top/width/height`，**看不到旋转后的真实覆盖区**。

**做法**：按端点位移预留净空。长边 L、角度 θ 时：

```
垂直方向单侧位移 ≈ (L / 2) × sin(θ)
```

例：宽 13.33"、倾斜 6° 的带子，单侧位移 ≈ 6.67 × 0.105 ≈ **0.70"**——它实际扫过的是「中心 y ± 0.7"」这条 1.4" 高的走廊，而不是标称的那 0.14"。所以：

- 先定**中心 y**，再用公式算出走廊上下界，确认走廊完整落在净空区内；
- 反过来也行：净空区只有多高，就配多小的角度。4° 的位移只有 8° 的一半。

**怎么验证**：只有渲染看图。这是 qa.py 结构上查不到的一类问题（形状框 ≠ 视觉覆盖区），必须靠闸门二。**实战教训**：黑色电影预设在这条上连错两轮——第一轮压住副标题，第二轮以为下移就够了，其实没算角度位移，第三轮才按公式定位。

## 17. 全宽色带的例外：结构 vs 装饰

**症状**：judge 报「全宽色带 = 模板脸」，但你用的其实是所声明来源里真实存在的结构组件。

**判据**：全宽色带只有在**它是声明来源的真实结构组件**、且**承载真实内容**时才允许。

- ✅ 允许：Material Design 2014 的顶部 App Bar（真实规范组件，内含标题）；蓝图风的工程图框与右下标题栏（真实图纸组件，内含字段）；构成主义的黑色口号块（内含反白大字）。
- 🚫 禁止：不装任何内容、只为「压住空白」或「看起来完整」的横条；每页复读的页脚带；分段进度条。

**做法**：派 judge 时主动说明这条色带的来源依据与它承载的内容，请它按「来源忠实度 + 是否承载内容」判，而不是按通用禁令判。说不出来源和内容的色带，就是装饰，删掉。

## 18. 中文禁则处理：标点不能落在行首行尾

**症状**：某一行以逗号或句号**开头**（「，逗号跑到了行首。」），或某一行以左引号**结尾**（「他说过一句话「」）。看着说不出哪里怪，但中文读者会立刻觉得不专业——这是排版基本功，不是风格偏好。

**原因**：显式换行时只顾了字数与词边界，没顾标点位置。自动换行的排版引擎会做禁则，但你手写断点时这层保护就没了。

**做法**：

- **行首禁则**——这些字符不能出现在一行开头：`，。、；：！？）》」』】〉” ’ % , . ; : ! ? ) ] }`
- **行尾禁则**——这些字符不能出现在一行末尾：`（《「『【〈“ ‘ ( [ {`
- 断点优先落在 `，。；：` 之后。
- 一行只剩一个标点被挤下来时，把上一行末尾的字一起挪下来（"避头尾"），而不是让标点单独成行。

**怎么验证**：`scripts/qa.py` 逐行检查这两条，命中记硬伤。

## 19. 文本宽度不要用单一估算常数

**症状**：明明留了余量的一行还是折行了（漏报）；或者明明装得下的一行被判超宽（误报）。

**原因**：用「全宽字算 1em、其余算 0.55em」这类单一常数估算宽度，误差非常大。实测同为 100pt：

| 字体 | 汉字 | 大写 A | 小写 a | 空格 |
|---|---|---|---|---|
| 微软雅黑 | 1.00 | **0.70** | 0.55 | 0.30 |
| 宋体 | 1.00 | 0.50 | 0.50 | 0.50 |
| Arial Black | 0.75 | **0.78** | 0.67 | 0.33 |

单一常数 0.55 对雅黑小写刚好，但**大写字母差 27%、Arial Black 差 42%**。全大写的英文标题最容易踩：估算说装得下，实际溢出一大截。

**做法**：用 Pillow 读真实字体度量。

```python
from PIL import ImageFont
f = ImageFont.truetype("C:/Windows/Fonts/msyhbd.ttc", 1000)   # 参考字号
width_pt = f.getlength(text) / 1000 * font_size_pt            # 按比例换算
```

用一个较大的参考字号（如 1000）再按比例换算，可避免整数字号的取整误差。字体文件缺失时才回落估算，并单独告警。

**顺带一个收获**：能读真实字体，就能顺手核对「这个字体本机到底有没有」，把 pitfalls #1 的静默替换风险变成可检查项。

## 20. 白字白底没人拦：对比度要在选色时按角色守住

**症状**：浅灰字压浅灰卡片、白字压纸白底——屏幕上勉强能看，投影和打印直接消失。写代码不会报错，qa.py 之外没有人提醒你。

**原因**：颜色一旦脱离预设的「角色」（TEXT / MUTED…）临场自造，就没有人保证它压在哪个底上。

**做法**：

- 文字颜色永远引用预设角色，不要临场写新色值；MUTED 压在哪个底色上，先对一眼预设标注的对比度。
- 半透明面板下的文字，按「透明度混合后的等效底色」验算，别按面板自己的色值算。

**怎么验证**：`python scripts/qa.py deck.pptx` 现在会查**显式指定 RGB** 的文字与其下方**不透明纯色填充**的 WCAG 对比度（<2.5 硬伤，<4.5 告警，大字放宽到 3.0）。压图、渐变、主题色继承查不了——这三类只有闸门二的 judge 能兜底。

## 21. 中文排进拉丁专用字体：渲染静默回退成衬线体

**症状**：用 Arial Black 排「一句主张」「谢谢」这类中文，本机看着是粗黑体？不——渲染器逐字形找覆盖，拉丁字体没有汉字字形，回退到默认中文字体（常是宋体一系），「编号用 Arial Black」的排印体系整页散架。更隐蔽的是宽度也跟着回退字体变，写代码时按什么量都不对。

**原因**：`fontFace` 按 run 写，但覆盖是按字形给的。Arial Black / Impact / Georgia / Segoe UI 一类只有拉丁字形。

**做法**：中文 run 用中文字体（微软雅黑 / 黑体 / 宋体），拉丁与编号才用 Arial Black 一类。`scripts/qa.py` 会对此类 run 告警，并按回退字体（雅黑）度量宽度，超宽检查不再失明。

## 22. 手机照片带 EXIF 方向：不管它就会躺倒

**症状**：用户在手机上竖着拍的照片，插进 PPT 里横躺 90°；在资源管理器里看是正的，在代码里读出来的像素却是躺的——两个软件对「方向」的解读不一致。

**原因**：相机不旋转像素，只在 EXIF 里记一个 Orientation 标记；有的软件认标记（显示正），有的不认（显示躺）。

**做法**：读图后立刻 `ImageOps.exif_transpose(img)` 把方向固化进像素，再裁切/缩放。`scripts/prep_assets.py` 的第一步就是这个，不要绕过它直接 `Image.open` 后处理。

**怎么验证**：处理完用看图软件与渲染图各看一遍——两处方向一致才算转正。

## 23. 图标字体缺字形：渲染出来是空白，不报错

**症状**：用了非内嵌的图标字体（或手动指定了一个字体里没有的码点/图标名），渲染结果是透明空图或豆腐块——页面上那块位置什么都没有，文件正常、代码正常、没有任何报错。

**原因**：字体按码点查找字形，找不到就画空；`ImageFont` 不会抛异常，`add_picture` 也不会。

**做法**：用技能内嵌的 Tabler 字体 + `assets/icons/semantic.json` 里的名字（`scripts/inject_icons.py` 会在语义表里查不到时直接报错并列出可用名，渲染为空时也会抛错）。若自己扩展图标名，先在对照表里渲染一遍确认字形存在。

**怎么验证**：注入后看渲染图——图标位置必须真的出现图形；qa 只能查有效 PPI，查不了「这块应该是图标但它是空的」。

## 24. 强调色直接压深底：风格说"就这样"，闸门说"不可读"

**症状**：某个深底预设（如蓝图纸的印泥红压蓝图蓝）规定强调色元素直接放在深色底上——按预设做，对比度只有 1.6:1，qa 判硬伤，投屏也确实看不清；做成浅底托板又觉得"偏离了预设"。公式、图标这类**图片型**强调元素更隐蔽：图片不进 qa 的文字对比度检查，红公式压蓝底会静默通过。

**原因**：色值是预设给的，但"压在什么底上"是排版决策；预设描述的是"关系"（深底 + 单一线色 + 一个红点缀），不是"红字必须裸压深底"。

**做法**：**强调色要压深底，就得有托板**。真实蓝图里的戳盖在浅色纸签上——给戳记一个线色浅底（白底红字）；公式图在深底上要么直接用亮色（LINE 色），要么加一块浅底托板。这不是偏离预设，是把预设的关系落对。

**怎么验证**：`qa.py` 现在会对 `icon:*` / `formula:*` / `figure:*` 命名的图片型图形做对比度兜底（**按最暗一档的墨色** vs 所在底色，<2.5 硬伤、<3.0 告警）；戳记若用空心形状（无填充），底色的判定走 slide 背景，注意核对。

## 25. 几何图与题面不符：画得挺好看，但那张图是错的

**症状**：重画一道几何题的图（triangle/圆/辅助线），线条干净、标注齐全，一切检查都过——但坐标实现与题面矛盾（题说 AB=AC，画出来不等长；题说钝角，画成锐角；高的垂足落在延长线上却画进了三角形内）。**这类错误没有任何机械检查能查出来**：语法、有效 PPI、对比度、渲染全都正常。

**原因**：图的美观由编译器保证，但"图是否忠实于题目"是语义问题；AI 手算坐标必然有出错概率，而错误不会报错，只会安静地误导读者——比不放图更糟。

**做法**：两件事缺一不可。①**先写作图依据**：把已知条件与作图意图用文字写出来（"△ABC 中 AB=AC、∠A=36°，作底边高 AD"），再写规格；②**把几何关系写进「约束」**：`{"类型":"直角","顶点":"A","边":["B","C"]}`、`{"类型":"等长","对象":[["A","B"],["A","C"]]}` 等，`scripts/inject_figure.py` 会逐条验算（等长/直角/平行/共线/中点/圆过点/角度/长度），超差即报错中止、文件不动，报告会给出实测值让你一轮改对。**不要用 `--force` 把超差糊过去**——那等于明知图画错了还交。

**怎么验证**：注入时看「约束 N 条验算通过」；交付前把渲染图和「作图依据」一起给闸门二的 judge 对照审（judge-prompt 的插图条目）；编译器只验你**声明过**的约束，漏声明或读错题面仍要靠 judge 与自己的复核。

## 26. 扫描件直接贴：灰底、歪斜、噪点，一眼就是"拍的"

**症状**：用户传了手机拍的卷子/书页，图片直接放进 PPT——整块灰黄底压在干净版面上、内容歪几度、边缘留着白边和噪点。就算版式再讲究，这块也立刻暴露"素材没处理"。

**原因**：手机拍摄天然带灰底（白平衡/环境光）、手抖造成的旋转、桌面背景的边；扫描仪出图则常有偏色。`prep_assets.py` 的默认项（EXIF/sRGB/裁切/降采样）不会动这些——它只保证不失真，不做"变好看"。

**做法**：规格里加 `"扫描件": true`（或给对象覆盖 `去斜/白底/裁白边/对比/去噪/留白`）。流水线：去噪（可选）→ 白底归一（边框分位数当底色、逐通道拉满）→ 去斜（Otsu 分墨迹 + 投影廓线估角，±8°内）→ 裁白边 → 对比。纯线稿再加 `"灰度": true`。清点模式会提示"疑似扫描件"。**默认裁切清洗优先、重绘按需**：只有需要重排、拆成多步、统一标签或做动画时才重画（重画另有 pitfalls #25 的约束纪律）。

**怎么验证**：处理报告会逐项写明（`扫描件：白底归一（×1.25） · 去斜 +3.00° · 裁白边（-90/-130px） · 对比 ×1.15`）；跑完打开 `_ready/` 里的图对一眼底色是否近白、内容是否摆正。去斜依赖 numpy（随 matplotlib 装），缺了会明确提示跳过而不是静默不转。

## 27. matplotlib 出图的两个默认陷阱：中文变方块、负号变方块

**症状**：用 matplotlib 画函数图/几何图，中文标签渲染成一个个空心方块（豆腐块），或坐标轴的负号 `-2` 变成方块/消失。代码不报错，图也生成了，只是没法看。

**原因**：matplotlib 默认字体不含汉字字形（逐字形回退失败）；且默认的 `axes.unicode_minus=True` 会用一个 U+2212 数学减号，多数西文字体有、部分环境下缺，就会变方块。

**做法**：`scripts/inject_figure.py` 已强制 `font.sans-serif` = 规格里的中文字体（默认微软雅黑，找不到会在候选里回退并告警）、`axes.unicode_minus=False`（用 ASCII 连字符当负号）、数学片段走 mathtext 的 cm 字体。自己写 matplotlib 时也要设这两项；中文与数学混排时把数学部分写进 `$...$`（如 `$\angle A=36^\circ$`），汉字交给中文字体——别把 `^` 写在 `$` 外面。

**怎么验证**：渲染后目验有没有方块；inject_figure 会在中文字体一个都没匹配上时直接告警"中文可能渲染成方块"。

## 28. matplotlib 透明底失效：transparent 和 facecolor 一起传，整张变不透明白底

**症状**：画出来的插图应该是透明底（好压在任意色底上），实际却整张不透明白底——浅色版面上看不出来（白压米白），一放到深色版面上就是一块刺眼的白方块；qa 的图片型对比度兜底也会因此把深色线条误算成"几乎不可见"（它取的是最暗墨色，全白图反而算出浅色）。**沉默的**：文件正常、图正常、代码不报错。

**原因**：matplotlib 的 `savefig(transparent=True, facecolor="auto")` —— 只要显式传了 `facecolor`（哪怕是字符串 `"auto"`），`transparent=True` 就被顶掉，画布按不透明面画满（3.11 实测：只传 `transparent=True` 得到 min alpha 0；再加 `facecolor="auto"` 得到 min alpha 255）。

**做法**：要透明就**只传** `transparent=True`，不要附加 `facecolor`；要实体底色才传 `facecolor=<色>` 并让 `transparent=False`。二者互斥，写成 if/else 分支而不是同时给。`scripts/inject_figure.py` 的 `_tight()` 已按这个写法修好（可选 `底` 参数给实体底色）。

**怎么验证**：注入后取 pptx 里 `figure:*` 的图片字节，转 RGBA 看 `alpha.min()` 是否为 0（有透明区）；或把图压到深色块上渲染一眼。qa 只查有效 PPI 与对比度，查不出"本该透明却是白底"。

## 29. 正文里用 △ □ ∠ ⊥ 这类符号：中文字体只画汉字四成大小，又小又细

**症状**：句子里写「求 △PAB 的面积」「如图 □ABCD」「∠A = 36°」，幻灯片上这些符号比周围汉字**明显小一圈、笔画也细一档**，整行像从纯文本里直接倒出来的——不是设计，是 LLM 味。奇怪的是 `①`、`½` 却不违和。

**原因**：这些是字体设计问题，不是字号问题。中文字体把几何/数学符号当"备用字形"，按较小的光学尺寸、较细的笔画绘制（实测微软雅黑 64px：`角` 墨迹高 0.98em、墨量 1454；`△` 只有 0.39em、墨量 165；`□` 0.50em/322，`○` 0.44em/174，`∠` 0.58em/340，`⊥` 0.62em/328）。而 `②`（0.92em/1005）、`½`（0.78em/730）是按汉字尺度设计的，所以不违和。更麻烦的是**各家字体比例还不一样**（雅黑/黑体/苹方各不同），同一页换台机器观感又变。

**做法**（按内容分三类，各有各的正确去处）：

- **句子里的形状/关系词** → 直接写汉字：「求**三角形** PAB 的面积」「**平行四边形** ABCD」「**角** A」。
- **数学表达式** → 别在文字流里排，把它拎出来独立成行，用 `$$…$$` 走 `scripts/inject_math.py`（数学字体按数学比例排版，`\triangle`、`\angle`、`\perp`、`\parallel` 都是正尺寸、粗细一致）。
- **要看的图形** → 用 `scripts/inject_figure.py` 真画出来（三角形就画三角形），或 `inject_icons.py` 取线性图标；别拿字符当图。
- **忠实引用原题**（卷子上就写的 `△PAB`）→ 优先转写为汉字或把该式提成公式图；确实要原样引用时，在交付说明里注明这是原题写法。

**怎么验证**：`qa.py` 会扫正文里的几何/数学符号（△▲□■◇◆○●∠⊥∥∵∴≌≅∽）并告警（不是硬伤——引用原题是合法场景）。注意 `inject_figure` 内部用 mathtext 渲染的 `$\triangle ABC$` 是图片、不是文字 run，不会被这条扫到，属正常。

## 30. ⚠️ pptxgenjs 表格外框高度 ≠ 行高合计：PowerPoint 静默裁掉下半截

**症状**：表格在预览图里完整，用 PowerPoint 打开只剩表头（或前一两行），下面被裁掉；表头是深色填充时观感就是「一大半被挡住了」。WPS / LibreOffice 完全正常——它们会按内容自动撑开外框。所以**渲染预览 100% 看不见这个故障**。

**原因**：pptxgenjs（实测 4.0.1）的 `addTable` 把表格外框 `p:graphicFrame/a:ext@cy` 取自 `options.h`，而 `rowH` 只写进 `<a:tr h>`——**外框高度从不按行高之和回填**（`dist/pptxgen.cjs.js` L5189 `cy="${cy || EMU}"`，缺 `h` 时固定退化成硬编码的 1 英寸）。宽度同理但更隐蔽：缺 `w` 时 `a:ext@cx` 退化成**页宽的 75%**（13.33" 画布上即 10.00"），`colW` 之和超过它就会横向裁切。库不校验两者一致性。危险用法有三：只给 `rowH` 不给 `h`；`h` 与 `rowH × 行数` 不符；给了 `colW` 而 `w` 偏小。

**做法**：**表格永远显式给 `h`，且 `h = rowH × 行数`；`w` 必须 ≥ `colW` 之和。** 用 `scripts/skeleton.js` 里的 `addTableSafe`（把这条约束变成代码，参数不自洽直接抛错，不静默生成坏文件）。多页表（`autoPage`）逐页同理。

**怎么验证**：**必须读结构，不能靠渲染**——本机渲染走 WPS/LibreOffice 会自动撑开。`qa.py` 现在会核对 `a:ext` 与 `a:tr@h` 之和 / `a:gridCol@w` 之和：外框矮于行高合计判硬伤，行高为 0（自动定高）告警，外框明显偏高告警。也可直接量：`外框 cy` vs `Σ a:tr h`（差值 >0.02" 即会被裁）。

## 31. ⚠️ 闸门某类检查因环境缺失整类关闭：报告里的「降级」不是通过

**症状**：`qa.py` 报「硬伤 0 · 告警 0」，看着是全部通过，其实有一整类检查根本没跑——最典型是 **jieba 没装或初始化失败，跨行劈词检查整类关闭**；还有 **Pillow 缺席**、**非 Windows 机器没有 `C:/Windows/Fonts`**，中文宽度只能用估算常数。这类情况下退出码仍是 0（旧行为），你和用户都会当成「查过了」。

**原因**：qa.py 的检查按可用依赖分组，缺依赖时早期版本直接 `_WORDS = {}` / 返回 `None` 静默降级——检查会死，而且死了没有任何症状。这与 #1「字体被静默替换」是同一类病：**不报错 ≠ 检查通过**。

**做法**：报告分**硬伤 / 告警 / 检查降级**三类；降级条目在报告顶部单列成块、计入退出码 2（`硬伤 0 · 告警 0 · 检查降级 N`）。**降级不是 deck 的错、也不是豁免理由**：交付说明里必须如实声明哪类检查没执行，不得声称该项已通过。要消掉降级就装齐依赖（`python -m pip install jieba pillow`）。

**怎么验证**：看报告首行与计数行的「检查降级 N」、以及紧随其后的 `[降级]` 块；装齐依赖后重跑应为「检查降级 0」。`scripts/selftest.py` 有对应断言（报告分诊 + 降级成块 + 干净稿 exit 0/2）。

## 32. ⚠️ 手写 XML 动画绕过了菜单模板：能播，但没有任何东西核对它

**症状**：用 `inject_anim.py --raw` 手写 `<p:timing>` 做菜单外的效果（路径动画、旋转、3D），文件能打开、动画也真的播——但**逐条断言没有跑**。菜单路线能核对的四件事（第几条是什么效果、打在哪个形状、什么触发、多长）在这里只有「文件能打开」和「读回条数」两项，报告标 `[降级]`。更危险的是手写片段有三类结构错会让 PowerPoint **静默丢弃**动画：spid 指向本页不存在的形状；根元素不是 `<p:timing>`；片段用了 slide 根元素没声明的命名空间前缀（slide 根只声明 `a`/`p`/`r`，写 `p159:` 就废，而 morph 系效果恰好用它）。

**原因**：菜单制的全部价值是「AI 不写 XML，模板全部抄自 PowerPoint 自己经 COM 生成的文件」，所以结构错不了。手写 XML 等于把这个前提撤掉；而 PowerPoint 对坏的 timing 树一贯是静默丢弃而不是报错——**能播 ≠ 是你写的那条**。

**做法**：逃生舱**默认关闭**，三重闸门缺一不可：命令必须带 `--raw`；脚本条目必须写 `"用户已同意": true` 与非空 `"原因"`；片段必须是 `<p:timing>` 根、spid 都在本页存在。**只有用户明确要求菜单外的效果、且已明确同意之后**才用，一次只放行必要的那几页。写入前校验会拦下：悬空 spid、非 timing 根、DOCTYPE/ENTITY、同页同时出现在 `pages` 与 `原始XML`、以及拼进整页后解析失败（抓未声明前缀）；被拒时文件保持原样。**别为了「更炫」主动开这个口子，更不要用它绕开点击/条数/时长预算。**

**怎么验证**：注入报告里那句 `⚠ 原始XML 逃生舱` 与 `[降级] S<n>` 行；退出码是 2 而不是 0。照常跑 `qa.py` 兜底——悬空 id 判硬伤，节拍/条数/时长护栏对手写 XML 一样生效。**逐条核对可以补回来**：给该条原始XML 加一份「断言」清单（形状/presetID/起始ms/时长ms/重复/参数，须覆盖该页全部效果），结构侧逐条核对不依赖 COM，另与 COM 读回的 `Timing.TriggerDelayTime`/`Duration` 交叉核对；全对则不再标降级。**别去累加往返文件里的 XML 延迟做断言**——PowerPoint 会重写节拍嵌套编码（实测把 800ms 写成「包装 1000 + 效果 800」），只有 COM 读回是权威口径。`scripts/selftest.py` 有 13 条断言覆盖三重闸门、结构拦截、正路径降级与断言清单。

## 33. ⚠️ 幻灯片自己翻页、讲到一半就跑掉：`p14:dur` 不是换片计时

**症状**：放映时这一页还没讲完就自己翻过去了；或者整份按固定节奏自动播、按都按不住；也可能点击换页失灵。常见误诊是跑去改 `<p:transition p14:dur="…">`——改那个没有用。

**原因**：`p14:dur` 是**切换动作本身的播放时长**（0.5–2s 的过渡动画），与换片计时毫无关系。真正让幻灯片自己翻页的只有三条来路：① 每页「设置自动换片时间」→ `<p:transition advClick="0" advTm="3000">`（`advTm` 单位毫秒；`advClick="0"` 连点击换页一起关掉），② 演示文稿级「使用计时 / 排练计时」→ `ppt/presentation.xml` 的 `<p:showPr useTimings="1">`，③ 放映方式选「展台(全屏幕)」→ `<p:showPr showType="kiosk">`，会循环播放且不受控。这三项**都不在本技能的写码路径里**（`inject_anim.py` 只写 transition 与 timing，不写 `advTm`/`advClick`，也不碰 showPr），所以文件里出现它们只可能是模板自带、或别的工具/手工设置加的。

**做法**：分清两件事——本技能的默认是「**页内**整页自动连播、**断点在翻页**」（首条「自动」+ 其余「之后」，页内 0 点击）：翻页由人控制，页内节奏由动画自己走完。这与「幻灯片自己翻页」完全不同。要保持人工控制节奏，就不要碰上面三项；反过来，用户**明确要**无人值守播放（展台循环、展映）是另一套需求，先确认再动，并写进交付说明。

**怎么验证**：`qa.py` 会拦这两类——某页 transition 带 `advTm` 或 `advClick="0"` 判告警；`p:showPr` 带 `useTimings="1"` 或 `showType="kiosk"` 判告警（报告前缀 `[deck]`）。手工核对：`python -c "import zipfile;print(zipfile.ZipFile('deck.pptx').read('ppt/presentation.xml').decode())" | grep -o '<p:showPr[^>]*>'`，以及逐页 `grep -o '<p:transition[^>]*>'`。
